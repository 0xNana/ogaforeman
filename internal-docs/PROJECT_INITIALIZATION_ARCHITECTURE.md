# Project Initialization — Phase 0 Domain Audit

Status: complete for Phase 0 (audit only). No import model or persistence
implementation is introduced by this phase.

## Canonical mapping

| Initialization concept | Existing implementation | Decision | Notes |
|---|---|---|---|
| Project | `app.domain.models.Project` | EXISTS | Already has name, description, location, timezone, dates, status, creator, timestamps, and date/timezone invariants. |
| Phase | none | CREATE | No canonical phase collection or model exists. Keep phase identity separate from task IDs. |
| Task | `app.domain.models.Task` | EXTEND | Supports schedule, status, trade, assignment, milestone, source references, and dependency IDs. Import provenance and phase linkage are missing. |
| Dependency | `Task.dependency_ids` plus `validate_task_dependency_graph` | EXTEND | Current representation is predecessor IDs on each task. It is sufficient for V1 Finish-to-Start, but import validation must detect duplicate edges and cycles before writes. |
| Material | `app.domain.models.Material` | EXISTS | Includes canonical ID, normalized name, aliases, unit, stock quantities, thresholds, and supplier metadata. `MaterialRepository` resolves aliases within authorized project scope. |
| Material ledger / inventory | `app.domain.materials.MaterialLedgerEntry` and `MaterialLedgerRepository` | EXISTS | Quantity changes are append-only and separate from material requirements. |
| Material requirement | none | CREATE | `MaterialRequest` is a procurement request, not a task-to-material requirement. A requirement model must reference canonical task/material IDs and units. |
| Issue | `app.domain.models.Issue` and `IssueService` | EXISTS | Supports blocker, delay-risk, safety, quality, and observation records with task links and evidence. |
| Daily log/report | `app.domain.models.DailyReport` and `ReportService` | EXISTS | Daily report is the current reporting projection; it is not an import source or draft. |
| Activity/audit | `app.domain.models.ActivityEvent`, `ActivityService`, `WorkflowAuditService` | EXISTS | Mutations use atomic activity recording and source/run linkage. Import lifecycle events should use the same contract. |
| Import record/draft | none | CREATE | No durable import state, draft envelope, source record, review state, or confirmation record exists. |
| Source provenance | `Task.source_refs` only | EXTEND | Existing task references are opaque IDs. A typed `SourceReference` and reusable provenance collection are required for all imported facts. |

## Persistence and authorization

`RepositoryStore` exposes typed repositories and cross-collection transactions.
`FirestoreRepositoryStore` is the production implementation; the in-memory
store is test-only. Project-scoped repositories and `AuthorizedProjectRepository`
provide the authorization boundary. Import writes must use one transaction per
confirmed import batch, preserve optimistic versions, and emit `ActivityEvent`s.

Canonical IDs are validated by the domain `CanonicalId` type and must be
generated by deterministic application code during import. Draft temporary IDs
remain local to the draft and must never be accepted as canonical Firestore IDs.

## Existing service/runtime boundaries

- Deterministic project/task/material/issue/report services already own domain
  mutations and validation.
- ADK `Runner` and durable `SessionService` own agentic orchestration and HITL
  continuation. Project initialization extraction must be another ADK workflow,
  not a second workflow runtime.
- Gemini/ADK may produce typed draft candidates only. Validation, ID generation,
  conflict handling, authorization, and commits remain deterministic services.
- `AgentRun` is an observable execution projection. It must not become the import
  draft or the import state machine.

## Phase 0 gaps and constraints

1. There is no `ProjectImportDraft`, `ProjectImport` record, phase model, material
   requirement model, source reference model, or import repository.
2. Existing task dependencies are adequate for the first Finish-to-Start import
   contract, but cycle and duplicate-edge checks must run against the complete
   draft before any canonical write.
3. Existing material stock and ledger models must not be reused to represent
   planned requirements; planned quantity and observed inventory are separate
   truths.
4. Existing project setup APIs create canonical records directly. Import APIs
   must add a review/confirmation boundary and must not silently reuse direct CRUD
   endpoints for unreviewed model output.
5. Import provenance needs a stable source/import identity so later reconciliation
   can diff a second confirmed import without replacing canonical records blindly.

## Phase 1 handoff

Phase 1 may create the typed contracts listed in `internal-docs/PROJECT_INIT.md`:
`ProjectImportDraft`, `ProjectDraft`, `PhaseDraft`, `TaskDraft`,
`DependencyDraft`, `MaterialDraft`, `MaterialRequirementDraft`,
`SourceReference`, `ImportWarning`, and `ImportConflict`. Those contracts should
be pure validation objects first, with no Gemini or Firestore dependency, and
must carry an explicit schema version.
